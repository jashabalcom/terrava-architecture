# ADR-0016: Prompt and guardrail configuration in DynamoDB, not in code

**Status:** Accepted
**Date:** 2025
**Scope:** AIInfraStack

## Context

Prompts are not code and they are not quite configuration. They change far more often than
application logic — a small wording change measurably shifts output quality — and iterating on
them is the main lever for improving AI features.

If prompts live in the Lambda source, every prompt tweak is a full deploy cycle: commit, CI,
CDK deploy, propagate. That's minutes to tens of minutes for a change that should take seconds
to try, which in practice means prompts get tuned rarely and in batches.

The compliance case is sharper. If a phrase turns out to produce non-compliant output
(ADR-0008), the fix should be live in minutes. "We'll ship it in the next deploy" is not an
acceptable answer to a compliance finding.

Two products with different AI personas — the investor advisor and the agent voice profile
(ADR-0013) — multiply the surface further.

## Options considered

### Option A — Prompts inline in Lambda source

Version-controlled, reviewable, atomic with the code that uses them. Rejected: deploy-cycle
latency on the fastest-moving artifact in the system, and no way to roll back a prompt without
rolling back code.

### Option B — Prompts in SSM Parameter Store

Better than code, no deploy needed. Rejected as the primary store: SSM has a low throughput
ceiling for high-frequency reads without caching, parameter size limits are restrictive for
long prompts, and it has no natural model for versioned records with metadata. SSM is still
used for configuration pointers, just not for the prompt bodies.

### Option C — Prompts in S3

Cheap, no size limits. Rejected: higher read latency than a key-value store, no conditional
writes, and versioning is object-level rather than record-level.

### Option D — A versioned prompt registry in DynamoDB

Single-digit-millisecond reads on the AI hot path, records carrying version and metadata,
conditional writes for safe updates, and the same store already holding the response cache and
token ledger (ADR-0006).

## Decision

**A versioned prompt and guardrail-configuration registry in DynamoDB**, read at request time
by the AI router and cached in the Lambda execution environment with a short TTL.

The registry holds prompts keyed by feature, product, and version. Guardrail policy config
lives alongside it, so a compliance change is a registry write.

**The active prompt version is part of the response cache key** (ADR-0006). Without that, a
prompt update would keep serving answers generated by the previous prompt for up to 24 hours —
a subtle bug that would make prompt iteration look ineffective.

## Consequences

**What got better**

- Prompt iteration is a registry write, not a deploy. Trying a variation costs seconds.
- A compliance fix goes live in minutes, which is what makes ADR-0008's policy layer
  operationally credible rather than theoretical.
- Versioned records mean rollback is pointing at the previous version — no code revert.
- A/B testing prompt variants is possible by routing a fraction of traffic to a different
  version and comparing against the token ledger and quality metrics.
- Two products' personas coexist as registry entries on shared AI infrastructure.

**What got worse**

- **Prompts left the code review process.** A prompt change can now reach production without a
  PR, which is exactly the property that makes it fast and exactly the risk. This needs
  compensating controls: an audit trail on registry writes, restricted write access, and
  ideally a staging-first promotion path.
- **Prompt and code can drift.** A handler expecting structured JSON and a prompt edited to
  produce prose will break at runtime, with nothing at build time to catch it. Output schema
  validation is not optional here.
- **A read on the AI hot path.** Mitigated by in-execution-environment caching, but that cache
  means a prompt update propagates over its TTL rather than instantly, and different warm
  Lambdas can briefly run different versions.
- **DynamoDB availability is now on the AI critical path.** A read failure needs a sane
  fallback — a last-known-good prompt bundled with the code — or an AI feature outage.
- Another store to back up and reason about in disaster recovery.

## Revisit when

- An unreviewed prompt change causes a production incident — that's the signal to add mandatory
  staging promotion rather than to move prompts back into code.
- Prompt count grows past what a flat registry manages comfortably and wants a proper prompt
  management tool with evaluation built in.
- Registry reads become a measurable share of AI request latency.
